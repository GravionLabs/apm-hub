# PBI pipeline

The per-PBI procedure of the `orchestrator` agent (and any runner that follows it). Behaviour is defined here once; the agent body keeps mode parsing, flags, description input, the `next`/`loop` sentences, delegation and the end report.

## Pipeline

0. Tech stack: load `detect-techstack` inline (never a forked subagent); keep the JSON. Invalid after one `-NoCache` retry → append `Ruling:` before guessing the stack.
1. **Read the issue**: dispatch `issue-reader` (haiku) with `<issue>` and keep only its JSON `{issue, type, title, digest, file, branch, bug, parent, tasks:[{n, state, merged, sha}], ledger}`; `{error}` → report it and stop. It resolves the integration branch (`branch`; `null` or `stale: true` → cut one with `github-release` first), saves the body to `file` (`.agents/<issue>/issue.md`), reads the `task`-labelled sub-issues (`pbi` children are separate PBIs) and computes "Task merged" per `references/task-issues.md`: for each task with `merged: true` and `state: open` close it with that rule's comment (`<branch>`, `<sha>` from the JSON) and skip it. Total tasks 0 → step 3 may plan; tasks exist but none open (all merged) → never re-plan, skip to step 5 (fallback for an empty `<first BASE>..HEAD`: `task-issues.md`). `ledger: resume` → the same-issue ledger rule below. Create `.agents/<issue>/` for reports and the ledger (add `.agents/` to `.git/info/exclude` when it is not ignored) and write the **context file** `.agents/<issue|adhoc>/context.md`: integration branch, issue title, `digest` and the path of `issue.md`, and the tech-stack JSON now, the exploration summary after step 2. Subagents get its path, never the pasted text; a subagent that needs more than the digest reads `issue.md`. On resume reuse the file when present, recreate it otherwise.
2. **Explore**: `explorer` with the issue number, title, `digest` and the paths of `context.md` and `issue.md` (it reads the body only when the digest is not enough) → summary of the affected code (≤ 300 words); append it to `context.md`.
3. **Plan** (plan mode; full or implement mode when the issue has no Task sub-issues, open or closed, and no `plan.json`): dispatch `planner` (never `general-purpose`) with the issue and the path of `context.md`; it runs `issue-planning` and writes `.agents/<issue>/plan.json`. Keep only the path, its summary and the open question count. Check `.agents/<issue>/plan.json` exists (re-dispatch `planner` once if missing, then ask). Approval gate: present the summary and open `questions[]`, grill the user on open `questions[]` per the skill's `references/grilling.md` (final round: approve the breakdown, which items to implement); then create issues per `references/publish.md` (plan mode stops here); an acceptance criterion or plan item the user defers here or at a later gate gets a `[Task]` sub-issue (unless one covers it), so it stays tracked and blocks closing. PBI → one task: no issue; ≥ 2 tasks: `[Task]` sub-issues (format: `github-issue` `references/task-issues.md`) are created at this gate. Existing Task sub-issues are used as they are, no planner and no `plan.json`: `model` sonnet, no `size: L` review (`task-issues.md`).
4. **Implement** per task, in blocking order on the PBI's one branch (Task sub-issues never get their own branch or PR): record `BASE=$(git rev-parse HEAD)`, never `HEAD~1`, then `implementer` (bug = label `bug` or `fix` title prefix, the reader's `bug: true`: tell it to load `diagnose` first; no loop possible → it returns `NEEDS_CONTEXT`, ask the user, do not re-dispatch) with the Task issue (goal, files, done-when), branch, the path of `context.md` (it reads it first), the plan item's `model` hint and report path `.agents/<pbi>/task-<nr>-report.md` (`<nr>` = Task issue number; the plan id, e.g. `p1`, when the single task has no issue). Commits are made here: subject `<type>: <desc> (#<pbi>)`, footer `Refs #<task>` (single task without issue: `Refs #<pbi>`), never `Closes`; details in `task-issues.md`. Keep only its ≤ 15-line reply, act on `Status`: `DONE` → next task; `DONE_WITH_CONCERNS` → correctness or scope concerns go back to the implementer first; `NEEDS_CONTEXT` → re-dispatch with the missing context; `BLOCKED` → stronger model or split. Never retry unchanged; a red suite twice → stop and ask. Issues are the source of truth, `plan.json` caches their numbers: a plan change edits the Task issue or adds one, then the cache. Resume: with a ledger skip tasks whose line is `Task #<nr>: DONE`, cross-checked with `git log -E --grep "^Refs #<task>$" origin/<integration-branch>..HEAD` (no duplicate task commits); without a ledger a task is done when that grep or "Task merged" finds a commit, and `<first BASE>` is `git merge-base HEAD origin/<integration-branch>`.
5. **Review**: after the last task review `<first BASE>..HEAD` with the issue number `<pbi>` (optional quick review after a task of `size: L`). Where a subagent may start subagents (Claude Code, and the runner's own session there) dispatch `review-lead` (sonnet) with the range, `<pbi>` and the path of `context.md`; it runs `review-fanout` in its own context and returns JSON `{verdict, mode, incomplete, failedDimensions, findings:[{severity, file, line, title, blocking}], truncated?, package, review}`; keep only that JSON and build the review summary from `findings`; an `{error}` or a reply that is not that JSON counts as `{error}`: re-dispatch once (append `Ruling: review-lead retry — <error> — one extra review`), then run `review-fanout` inline (`Ruling: review-lead fallback inline — <error> — duplicate review cost`); when `review-lead` already wrote a package file (`.agents/<pbi>/review-<n>.diff`) or `review.json`, say so in the ruling and reuse that package path instead of building a second one. Everywhere else (Copilot CLI, OpenCode, VS Code Copilot, no subagent tool) run one `review-fanout` inline as before: it writes the package file and fans out to `reviewer`, the diff never enters your context. `reviewer` is dispatched only from `review-fanout`, only after that package file exists and is non-empty, and never after the PR phase (step 6). Show the review summary (one line per finding, MEDIUM/LOW included; hidden by `--no-review-summary`) and ask which advisories to fix, or with `--fix-advisories` apply that policy without asking (it wins over `--no-review-summary`; re-applied to each re-review, leftovers go to the PR body); the selected ones join the fix round, the rest go to the PR body (`orchestrator-gates.md`). `CHANGES_REQUESTED` (or selected advisories) → fix rounds: the implementer gets the blocking and selected findings as a list plus the `review.json` path, never the package; rounds 1–2 resume the same implementer (Claude `SendMessage` to its agent id, OpenCode resume the task), round 3 a fresh implementer one model tier up (Copilot subagents are stateless: fresh implementer with findings, context path and report path); still blocked → ask the user.
6. **Pull request**: dispatch `pr-writer` (sonnet) with `<pbi>`, branch, integration branch, the unselected advisories, the not-delivered list (every open Task sub-issue without a `Refs #<task>` commit on the integration branch or in `<first BASE>..HEAD`, plus deferred criteria without a Task) and the paths of `context.md` and the ledger; it runs `github-pull-request` into the integration branch, one PR per PBI with `Closes #<pbi>` (non-empty not-delivered list: `Refs #<pbi>` and `## Not delivered`, the release then leaves the PBI open) and the task list `#<task> — <sha>` (single task: `#<pbi> — <sha>`) in the body, and returns `{number, url}` plus `closes` or `refs` only, which you record as `Phase pull-request: complete — <url>` (with `refs`: append ` — refs, not delivered: #<a>, #<b>`). The Task commits are already made, no extra commit; never merge. `{error}` → re-dispatch once with the error, then ask.

## Per-PBI rules
- Model per dispatch (Claude: `model` on the `Agent` call, never omitted): `issue-reader` haiku; `explorer` haiku; `planner` inherit; `implementer` defaults to sonnet (frontmatter), pass `inherit` or stronger explicitly for integration and design tasks; `review-lead` sonnet; `reviewer` sonnet; `pr-writer` sonnet; final verify inherit. A runner (`pbi-runner`, Claude Code loop) has no inherited model to pass on and pins `planner`, final verify and fix round 3 to opus, `issue-reader` and `explorer` to haiku, `implementer`, `review-lead`, `reviewer` and `pr-writer` to sonnet (opus where the plan item says `inherit`); its agent file lists the same pins. OpenCode takes the model from the agent file, Copilot has no override. A cheaper model that needs 2–3× the turns costs more: sonnet is the floor for prose-only tasks.
- Ledger `.agents/<issue>/progress.md`, written only with `pwsh <skills dir>/github-issue/scripts/Add-LedgerLine.ps1 -Issue <issue|adhoc> -Line '<text>'` (from the client's skills dir, as `.claude/skills`, `.opencode/skills`, `.agents/skills`, `.github/skills` or the `~/` one; also creates the directory; never a shell redirect), first line `# orchestrator ledger — issue #<issue> — branch <branch>`. Append `Phase <name>: complete — <SHAs|PR URL|n/a>` after each phase, `Task #<nr>: <status> — <sha> — model <name>` after each task, `Fix round <r>: <result> — model <name>` after a fix (`<name>` = the model the implementer was dispatched with, `inherit` when unpinned; resume matches only the `Task #<nr>: DONE` prefix, lines without the suffix stay valid), `Ruling: <decision> — <why> — <cost if wrong>` for every call you make yourself; gates still go to the user, a ruling never replaces one.
- Same-issue ledger exists (header `# orchestrator ledger`, or the older `# lead ledger` / `# dev-workflow ledger`; legacy headers: removal version in CONTRIBUTING.md legacy table) → resume at the first phase without `complete` and say so in one line; another issue's ledger stays untouched. After compaction trust the ledger and `git log` over memory.

## Gate points

Each of these is an approval gate: it goes to the user (a runner returns it as a `GATE` reply with the question), never decided alone. Detail in `orchestrator-gates.md`.

1. Plan gate (step 3): the breakdown, open `questions[]`, which items to implement.
2. Review summary (step 5): which advisories to fix (not asked with `--fix-advisories`).
3. `CHANGES_REQUESTED` still blocked after fix round 3 (step 5).
4. Red suite twice on one task (step 4).
5. `NEEDS_CONTEXT` from a bug implementer that has no feedback loop (step 4).
6. Any other question at a gate with no question tool: append `Gate: <question>` to the ledger and stop.

A runner appends `Gate: <question>` for every item above before it returns the `GATE` reply, and `Ruling: <question> - user - <answer>` when it is resumed with the answer.
