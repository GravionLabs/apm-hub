# PBI pipeline

The per-PBI procedure of the `orchestrator` agent (and any runner that follows it). Behaviour is defined here once; the agent body keeps mode parsing, flags, description input, the `next`/`loop` sentences, delegation and the end report.

## Pipeline

0. Tech stack: load `detect-techstack` inline (never a forked subagent); keep the JSON and its `state_dir` (`<state>`, absolute; record it in `context.md`, pass it in every subagent prompt; `issue-reader` and `planner` get it cwd-relative when it lies under the cwd, e.g. `.git/agents`, so their rooted OpenCode write rules match). Invalid after one `-NoCache` retry → append `Ruling:` before guessing the stack.
1. **Read the issue**: dispatch `issue-reader` (haiku) with `<issue>`, `<state>` and keep only its JSON `{issue, type, title, digest, file, branch, bug, parent, tasks:[{n, state, merged, sha}], ledger}`; `{error}` → report it and stop. It resolves the integration branch (`branch`; `null` or `stale: true` → cut one with `github-release` first), saves the body to `file` (`<state>/<issue>/issue.md`), reads the `task`-labelled sub-issues (`pbi` children are separate PBIs) and computes "Task merged" per `references/task-issues.md`: for each task with `merged: true` and `state: open` close it with that rule's comment (`<branch>`, `<sha>` from the JSON) and skip it. Total tasks 0 → step 3 may plan; tasks exist but none open (all merged) → never re-plan, skip to step 5 (fallback for an empty `<first BASE>..HEAD`: `task-issues.md`). `ledger: resume` → the same-issue ledger rule below. Create `<state>/<issue>/` for reports and the ledger and write the **context file** `<state>/<issue|adhoc>/context.md`: integration branch, issue title, `digest` and the absolute path of `issue.md`, and the tech-stack JSON now, the exploration summary after step 2. Subagents get its path, never the pasted text; a subagent that needs more than the digest reads `issue.md`. On resume reuse the file when present, recreate it otherwise.
1b. **Checkout** (modes full and implement and every PBI of `next` and `loop`; `plan` edits no code and takes none): right after `issue-reader`, before any work on the branch, run `pwsh <skills dir>/github-issue/scripts/Enter-Checkout.ps1 -Issue <pbi> -Branch <type>/<pbi>-<slug> -Base <integration branch>` (branch name per `conventional-commits.md`; an existing branch of the PBI is kept). It prints `{path, worktree, branch, base, lease}`: the main checkout when it is free, `.worktrees/<pbi>` when it is busy. Write `path` and `worktree` into `context.md`. From here on every subagent prompt says "work in `<path>`" (Bash: `cd <path>` first; Read, Edit and Write: absolute paths under `<path>`), and your own git commands use `git -C <path>`. Resume: the lease of the same issue returns the same `path`. Description runs call it right after the PBI is created (`orchestrator-gates.md` "Description input", step 8). A non-zero exit → report the first error line and stop (FAILED). Release rules: "Checkout" in the per-PBI rules.
2. **Explore**: `explorer` with the issue number, title, `digest` and the paths of `context.md` and `issue.md` (it reads the body only when the digest is not enough) → summary of the affected code (≤ 300 words); append it to `context.md`.
3. **Plan** (plan mode; full or implement mode when the issue has no Task sub-issues, open or closed, and no `plan.json`): dispatch `planner` (never `general-purpose`) with the issue and the path of `context.md`; it runs `issue-planning` and writes `<state>/<issue>/plan.json`. Keep only the path, its summary and the open question count. Check `<state>/<issue>/plan.json` exists (re-dispatch `planner` once if missing, then ask). Approval gate: present the summary and open `questions[]`, grill the user on open `questions[]` per the skill's `references/grilling.md` (final round: approve the breakdown, which items to implement); then create issues per `references/publish.md` (plan mode stops here); an acceptance criterion or plan item the user defers here or at a later gate gets a `[Task]` sub-issue (unless one covers it), so it stays tracked and blocks closing. PBI → one task: no issue; ≥ 2 tasks: `[Task]` sub-issues (format: `github-issue` `references/task-issues.md`) are created at this gate. Existing Task sub-issues are used as they are, no planner and no `plan.json`: tier `standard`, no `size: L` review (`task-issues.md`).
4. **Implement** per task (in `<path>` of step 1b) on the PBI's one branch (Task sub-issues never get their own branch or PR; local task branches of a wave are never pushed), in **waves** of up to `--parallel <n>` independent Tasks (default, budget, wave rule, worktrees, cherry-pick integration, `Wave` ledger line and resume of unintegrated task branches: `references/task-waves.md`; `--parallel 1` or one open Task = the sequential run described here): record `BASE=$(git rev-parse HEAD)` once, before the first wave, never `HEAD~1`, then `implementer` (bug = label `bug` or `fix` title prefix, the reader's `bug: true`: tell it to load `diagnose` first; no loop possible → it returns `NEEDS_CONTEXT`, ask the user, do not re-dispatch) with the Task issue (goal, files, done-when), branch, the path of `context.md` (it reads it first), the plan item's `tier` (dispatched at that tier's model, `references/model-policy.md`) and report path `<state>/<pbi>/task-<nr>-report.md` (`<nr>` = Task issue number; the plan id, e.g. `p1`, when the single task has no issue). Commits are made here: subject `<type>: <desc> (#<pbi>)`, footer `Refs #<task>` (single task without issue: `Refs #<pbi>`), never `Closes`; details in `task-issues.md`. Keep only its ≤ 15-line reply, act on `Status`: `DONE` → next task; `DONE_WITH_CONCERNS` → correctness or scope concerns go back to the implementer first; `NEEDS_CONTEXT` → re-dispatch with the missing context; `BLOCKED` → one tier up or split. Never retry unchanged; a red suite twice → stop and ask. Issues are the source of truth, `plan.json` caches their numbers: a plan change edits the Task issue or adds one, then the cache. Resume: with a ledger skip tasks whose line is `Task #<nr>: DONE` (written only after the commits are on the PBI branch; an unintegrated local task branch is integrated, not re-implemented), cross-checked with `git log -E --grep "^Refs #<task>$" origin/<integration-branch>..HEAD` (no duplicate task commits); without a ledger a task is done when that grep or "Task merged" finds a commit, and `<first BASE>` is `git merge-base HEAD origin/<integration-branch>`.
5. **Final-Verify, then review**: after the last task run **Final-Verify** once: dispatch the `verify-project` skill in a forked general-purpose context (Claude Code: `Agent` with `subagent_type: general-purpose`, model haiku, it only runs commands; OpenCode/Copilot: the equivalent read-only subagent, else inline) with the output path `<state>/<pbi>/verify.json`; it writes `{status, summary, tests}` there and you keep only that JSON. Append `Phase verify: <ok|fail> — tests <n>/<m>` to the ledger. Red (`status: fail`) → fix round with the failure list (implementer, targeted rule), then Final-Verify again; red twice → gate to the user (`orchestrator-gates.md`). Final-Verify also runs once after the LAST fix round (never per fix round, except after an advisory-only round, where it is part of the light check); the review verdict plus a green `verify.json` gate the PR phase. Then review: after the last task review `<first BASE>..HEAD` with the issue number `<pbi>` (optional quick review after a task of `size: L`). Where a subagent may start subagents (Claude Code, and the runner's own session there) dispatch `review-lead` (sonnet) with the range, `<pbi>` and the path of `context.md`; it runs `review-fanout` in its own context and returns JSON `{verdict, mode, incomplete, failedDimensions, findings:[{severity, file, line, title, blocking}], suppressed, truncated?, packageTokens, oversize?, packageFile, review}`; keep only that JSON and build the review summary from `findings`; an `{error}` or a reply that is not that JSON counts as `{error}`: re-dispatch once (append `Ruling: review-lead retry — <error> — one extra review`), then run `review-fanout` inline (`Ruling: review-lead fallback inline — <error> — duplicate review cost`); when `review-lead` already wrote a package file (`<state>/<pbi>/review-<n>.diff`) or `review.json`, say so in the ruling and reuse that package path instead of building a second one. Everywhere else (Copilot CLI, OpenCode, VS Code Copilot, no subagent tool) run one `review-fanout` inline as before: it writes the package file and fans out to `reviewer`, the diff never enters your context. `reviewer` is dispatched only from `review-fanout`, only after that package file exists and is non-empty, and never after the PR phase (step 6). Append `Phase review: complete — <sha> — package ~<n>k tokens[ — skipped <dim>,<dim> (size small)]` (`<n>` = `packageTokens`/1000 rounded, or `package.tokensEstimated` of `review.json`; the skipped part is read from `skippedDimensions` of `review.json`, omitted when empty) to the ledger and show `oversize` in the review summary. Show the review summary (one line per finding, MEDIUM/LOW included; hidden by `--no-review-summary`) and ask which advisories to fix, or with `--fix-advisories` apply that policy without asking (it wins over `--no-review-summary`; re-applied to each re-review, leftovers go to the PR body); the selected ones join the fix round, the rest go to the PR body (`orchestrator-gates.md`). After the first `APPROVE`, advisory-only rounds are capped by `--advisory-rounds` (default 1, `orchestrator-gates.md`); the re-review after an advisory-only round is the light check (Final-Verify plus a `correctness`-only delta review). `CHANGES_REQUESTED` (or selected advisories) → fix rounds: the implementer gets the blocking and selected findings as a list plus the `review.json` path, never the package, and the files of the findings; its prompt states the scope rule: the issue wins over a conflicting finding, and a finding that needs a new module, a new fallback or retry path, new I/O or a new security mechanism is `deferred`, not implemented, except a blocking security finding, which is never deferred; the implementer answers every finding with `fixed | declined: <reason> | deferred: out of scope — <need>`; after each fix round merge those statuses into `<state>/<pbi>/rulings.json` (read it, replace the entry with the same `file`, `line` and `title`, append the others, never overwrite the file; array of `{file, line, severity, title, status, reason?}`, `status` one of `fixed|declined|deferred|pr-body`; also append every advisory sent to the PR body, i.e. not selected for a fix round, as `pr-body` with the same merge rule; this merge completes before any re-review is dispatched) and, when either count is > 0, append `Ruling: <n> declined, <k> deferred findings` to the ledger with `<n>` and `<k>` counted over the whole file; its prompt names the targeted test rule (build only when compiled sources changed, tests of the changed paths, never the full suite in a fix round); rounds are counted per task from its first blocking review (`model-policy.md` "Escalation in the fix loop"): round 1 resumes the same implementer (Claude `SendMessage` to its agent id, OpenCode resume the task); round 2, the second `CHANGES_REQUESTED` with a blocking finding on the same task, dispatches a fresh implementer one tier up; round 3 resumes that escalated implementer once; still blocked after round 3 → gate to the user. Advisory-only rounds (selected findings, none blocking) and a `DONE_WITH_CONCERNS` reply resume the same implementer at its tier, never escalate and are not counted for escalation, only toward `--advisory-rounds` (Copilot subagents are stateless: fresh implementer at the round's tier with findings, context path and report path). Re-review after a fix round with blocking findings covers `<last review HEAD>..HEAD` (record `HEAD` at each review) with the dimensions that had blocking or selected findings plus `correctness` (a dimension skipped for size is never added back: it cannot have findings); `review-lead` gets range, dimension list, the previous round's `review.json` path and `<state>/<pbi>/rulings.json` and passes them to `review-fanout`, whose package then holds only the fix diff plus the earlier findings (fixed/open/pr-body/declined), not the full diff; advisories matching a `pr-body`, `declined` or `deferred` ruling are suppressed and counted in the reply key `suppressed`. After the LAST fix round Final-Verify runs once (see above), then the PR phase; the exception is an advisory-only round, whose light check runs Final-Verify right after it.
6. **Pull request** (only after the review verdict and a green `<state>/<pbi>/verify.json`): with `k` ≥ 1 deferred findings in `rulings.json` first settle the follow-ups per `orchestrator-gates.md` "Follow-up PBIs for deferred findings" (interactive with a question tool: ask once; headless and `pbi-runner`: no question, no `Gate:`, append `Ruling: <k> deferred findings — follow-up candidates in PR body`), then dispatch `pr-writer` (sonnet) with `<pbi>`, branch, integration branch, the unselected advisories, the declined findings (with reason) and the deferred findings (with need) from `rulings.json` (or its path `<state>/<pbi>/rulings.json`), plus the follow-up `#<n>` per deferred finding when step 6 created one, the not-delivered list (every open Task sub-issue without a `Refs #<task>` commit on the integration branch or in `<first BASE>..HEAD`, plus deferred criteria without a Task) and the paths of `context.md` and the ledger; it runs `github-pull-request` into the integration branch, one PR per PBI with `Closes #<pbi>` (non-empty not-delivered list: `Refs #<pbi>` and `## Not delivered`, the release then leaves the PBI open) and the task list `#<task> — <sha>` (single task: `#<pbi> — <sha>`) in the body (declined findings join `## Advisories not fixed`, deferred ones go to `## Follow-up candidates`; deferred findings are not acceptance criteria and keep `Closes`), and returns `{number, url}` plus `closes` or `refs` only, which you record as `Phase pull-request: complete — <url>` (with `refs`: append ` — refs, not delivered: #<a>, #<b>`). The Task commits are already made, no extra commit; never merge. `{error}` → re-dispatch once with the error, then ask.

## Per-PBI rules
- Model per dispatch: every dispatch runs at a tier (`fast`, `standard`, `strong`) of `references/model-policy.md`, which maps attributes to tiers and tiers to model ids per client (Claude: the tier's model named explicitly on every `Agent` call, never omitted and never inherited; the orchestrator itself runs at `standard`): `issue-reader` fast; `explorer` fast; `planner` strong; `implementer` the plan item's `tier` (no plan item: standard); fix round 2 one tier up; `review-lead` standard; `reviewer` standard (`strong` where `model-policy.md` says so); `pr-writer` standard; Final-Verify fast. Orchestrator and runner (`pbi-runner`, Claude Code loop) never inherit a model; each pins `planner` and fix round 2 to strong, `issue-reader`, `explorer` and final verify to fast, `implementer`, `review-lead`, `reviewer` and `pr-writer` to standard (the implementer at strong where the plan item's tier says so); the runner's agent file lists the same pins as Claude models. OpenCode and Copilot take the model from the agent file (variants: `model-policy.md`). A cheaper model that needs 2–3× the turns costs more: `standard` is the floor for prose-only tasks.
- Ledger `<state>/<issue>/progress.md`, written only with `pwsh <skills dir>/github-issue/scripts/Add-LedgerLine.ps1 -Issue <issue|adhoc> -Line '<text>'` (from the client's skills dir, as `.claude/skills`, `.opencode/skills`, `.agents/skills`, `.github/skills` or the `~/` one; also creates the directory; never a shell redirect), first line `# orchestrator ledger — issue #<issue> — branch <branch>`. Append `Phase <name>: complete — <SHAs|PR URL|n/a>` after each phase, `Phase verify: <ok|fail> — tests <n>/<m>` after each Final-Verify, `Task #<nr>: <status> — <sha> — model <name>` after each task, `Wave <w>: <task list> — integrated <sha>|conflict #<task>` after each wave (and `Worktree #<task>: install <s>s`; `task-waves.md`), `Fix round <r> (#<task>): <result> — model <name> — tests <n>/<m>` after a fix (`<nr>` and `<task>` = the Task issue number, the plan id (e.g. `p1`) for a single task without issue, as in its report path; `<name>` = the dispatched model, at fix round 2 the escalated one so `retro` sees the escalation; `Add-LedgerLine.ps1` and the hooks put an ISO-8601 UTC prefix `2026-10-21T15:19:46Z ` before every line, so never write one yourself; resume matches only the `Task #<nr>: DONE` prefix after the optional timestamp, older lines without these parts, including the tests part, stay valid, as do lines without the timestamp; `retro` computes durations from the timestamps), `Ruling: <decision> — <why> — <cost if wrong>` for every call you make yourself; gates still go to the user, a ruling never replaces one.
- Checkout (step 1b; the same scripts on Claude Code, Copilot CLI and OpenCode): `Enter-Checkout.ps1 -Issue <pbi> -Branch <type>/<pbi>-<slug> -Base <integration branch>` takes the checkout, `pwsh <skills dir>/github-issue/scripts/Exit-Checkout.ps1 -Issue <pbi>` gives it back. Every run end that appended `Ledger complete.` (full, implement, `next`, each PBI of `loop`, `pbi-runner` DONE) releases it right after that line: a clean worktree is removed, a dirty one is kept and reported, the main checkout is only unleased. A gate stop (also the headless `Gate:` stop), BLOCKED and FAILED keep the lease: the report prints `Checkout kept: <path>` (and, for a worktree, that the resume finds it there), and the next `Enter-Checkout.ps1` of the same issue returns that path. `Add-LedgerLine.ps1` renews the lease heartbeat with every ledger line; a lease without a line for 120 minutes is stale and may be taken over.
- Same-issue ledger exists (header `# orchestrator ledger`, or the older `# lead ledger` / `# dev-workflow ledger`; legacy headers: removal version in CONTRIBUTING.md legacy table) → resume at the first phase without `complete` and say so in one line; another issue's ledger stays untouched. After compaction trust the ledger and `git log` over memory.

## Gate points

Each of these is an approval gate: it goes to the user (a runner returns it as a `GATE` reply with the question), never decided alone. Detail in `orchestrator-gates.md`.

1. Plan gate (step 3): the breakdown, open `questions[]`, which items to implement.
2. Review summary (step 5): which advisories to fix (not asked with `--fix-advisories`, nor once `--advisory-rounds` is reached: the limit answers without asking).
3. `CHANGES_REQUESTED` still blocked after fix round 3 (step 5: round 2 escalated one tier, round 3 resumed it once).
4. Red suite twice on one task (step 4), or Final-Verify red twice (step 5).
5. `NEEDS_CONTEXT` from a bug implementer that has no feedback loop (step 4).
6. Any other question at a gate with no question tool: append `Gate: <question>` to the ledger and stop.

A runner appends `Gate: <question>` for every item above before it returns the `GATE` reply, and `Ruling: <question> - user - <answer>` when it is resumed with the answer.

Not a gate: the follow-up PBI question for deferred findings (step 6) is asked in interactive runs only, once per PBI and only with ≥ 1 deferred finding; never a runner reply and never a `Gate:` line.
