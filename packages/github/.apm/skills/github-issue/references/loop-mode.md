# Loop mode (`orchestrator loop <feature|epic>`)

Runs the open PBIs of a Feature or Epic one after another in one session: select per `next-selection.md`, run the PBI as **full**, record it, reselect. `<nr>` is the loop target (the Feature or Epic); `loop` takes no description (same answer as `next`: it needs a Feature or Epic number, stop). Everything a `full` run does per PBI (branch, tasks, review, PR, per-PBI ledger) is unchanged.

## Loop ledger

- Path `<state>/loop-<nr>/progress.md`, written only with `pwsh <skills dir>/github-issue/scripts/Add-LedgerLine.ps1 -Issue loop-<nr> -Line '<text>'` (creates the directory; never a shell redirect). `Add-LedgerLine` writes no headers: write the header line `# orchestrator ledger — loop #<nr> — branch <branch>` yourself, only when `<state>/loop-<nr>/progress.md` does not exist yet.
- A PBI gets its checkout in step 1b of `pbi-pipeline.md`: `Enter-Checkout.ps1 -Issue <pbi> -Branch <type>/<pbi>-<slug> -Base <integration branch>` (main checkout when free, `.worktrees/<pbi>` when busy; same script on every client; it also sets the project Status to `In Progress` when a project is configured, `Exit-Checkout.ps1` leaves Status as is; `pbi-runner` runs the step itself). After the PR phase of each PBI: `Loop: PBI #<nr> done — <pr>`, `Ledger complete.` in the PBI's ledger, then `Exit-Checkout.ps1 -Issue <pbi>` (runner mode: the runner does the last two on DONE). A parked PBI's lease is freed by `Set-ParkedGate.ps1` with `Exit-Checkout.ps1 -Keep` (worktree kept, prints `Checkout kept: <path>`); `runner blocked` and `runner failed` keep the lease and print `Checkout kept: <path>`; the next loop run finds the checkout through the same-issue lease or, after parking, the branch.
- Needs sync: after the `Next PBI:` announcement and the bind, and again after each `Loop: PBI #<nr> done — <pr>` line (also for a PBI that ends `parked` or `merged`), run `pwsh <skills dir>/github-project/scripts/Sync-ProjectNeeds.ps1 -Issue <pbi> -IncludeParents`. It prints one line; a failure (script missing, no project, non-zero exit) is ignored, never a stop. `PROJECT_SYNC_OFF=1` skips it. Runner mode: the primary runs it after the bind and after the `DONE` line (slot filling included).
- At each PBI boundary: `Loop: PBI #<nr> started` (written by `-Bind`, below). After the PR phase of each PBI: `Loop: PBI #<nr> done — <pr>` (the PR URL from `pr-writer`).
- A headless gate parks the PBI: `Loop: PBI #<nr> parked — <question>` (written by `Set-ParkedGate.ps1 -Loop <nr>`, see Stop conditions); the loop goes on with the next selectable PBI. A `/ruling <answer>` comment answers it (`next-selection.md`, `Get-ParkedRuling.ps1`).
- At the end: `Loop: stopped — <reason>` with exactly one of `nothing selectable` (also when only parked `needs-decision` PBIs remain), `context warning`, `pbi cap`, `user stop`; runner mode adds `runner blocked` and `runner failed`.
- Per-PBI ledgers `<state>/<pbi>/progress.md`, their `Phase`, `Task`, `Fix round` and `Ruling:` lines are unchanged: a ruling is recorded in the ledger of the PBI it was made for, never in the loop ledger. The `hooks` `SubagentStop` ledger and the OpenCode plugin skip `loop-<nr>` directories and write orchestrator subagent lines to the per-PBI ledger of the bound PBI (loop marker below), else of the branch issue (rules: [orchestrator.md § Hooks](https://github.com/GravionLabs/apm-hub/blob/main/docs/orchestrator.md#hooks)).
- PBI boundary: right after announcing `Next PBI: #<nr> <title>` and before dispatching `issue-reader`, create `<state>/<pbi>/progress.md` with its header (`Add-LedgerLine.ps1 -Issue <pbi> -Line '# orchestrator ledger — issue #<pbi> — branch <branch>'`), then bind the loop to it: `Add-LedgerLine.ps1 -Issue <pbi> -Bind loop-<nr>` appends `Loop: PBI #<pbi> started` to the loop ledger and writes the marker of the checkout it runs in, `<state>/current.d/<key>` (`<key>` = the lease key of that checkout: first 16 hex of the SHA-256 of its absolute path; content `<pbi> loop-<nr>`, plus the issue number of the branch it ran on when that is another issue): one marker per checkout, so loops in different checkouts do not overwrite each other. The hook and the plugin read the marker of the payload's checkout (when none exists for it, the one marker whose PBI holds a live lease; the old single `<state>/current` only while no `current.d/` exists) and use it before the branch number only while the loop ledger's last `Loop: ` line is not a `Loop: stopped` line and the current branch carries no issue number, `<pbi>`, the recorded number, or a number with a `Loop: PBI #<nr> done` line; any other issue branch wins. So the stop lines of the new PBI's `issue-reader`, `explorer` and `planner` land in its own ledger although its branch is not checked out yet. `-Bind` fails without the PBI ledger; every stop runs `Add-LedgerLine.ps1 -Unbind` (from the checkout the loop was bound in) right after the `Loop: stopped` line. The reader then reports `ledger: resume` on a header-only ledger, which resumes at step 1: no difference to a fresh start.

## Selection and reselection

Same algorithm as `next-selection.md` on the loop target, run by the orchestrator itself with `gh` (sub-issues of `<nr>`, recursive for an Epic): candidates in sub-issue order, drop merged, blocked (`needs-decision` without an `answered` `/ruling` comment per `Get-ParkedRuling.ps1`, open, unmerged blocker) and in flight; a PBI parked earlier in the same loop run becomes selectable again once answered, and its pick applies the ruling (`-Apply`) before `Next PBI:`; a candidate whose blockers are all merged stays selectable and is reported `blocker #<n> merged, closes at release`. Announce each pick with `Next PBI: #<nr> <title>`, then run it as **full** (the PBI becomes `<issue>`). The selection never reads the `Loop: … done` lines: a finished PBI drops out because its PR is open (`waiting for merge: PR #<n>`) or merged (`merged, closes at release`); a PBI whose PR was closed without merge is selected again. Never merge a PR to make the next PBI selectable. A blocked-by chain inside one Feature ends the loop after the first PBI of the chain while its PR is open: that is the normal `nothing selectable` stop with the `waiting for merge` reason, not an error. Once the first PBI of the chain is merged, the next one is selectable.

A `plan` is never run inside the loop beyond the plan gate of a PBI without Task sub-issues (step 3 of `full`).

## Stop conditions

Checked before every reselection, in this order:

1. **Context warning**: the warning text injected by the `hooks` package appeared in this session. There is no file to read: the signal is that the text has appeared in your own context. Clients differ: Copilot CLI (`postToolUse`) injects it after any tool call, so it fires inside a running loop; Claude Code (`UserPromptSubmit`) and OpenCode (`chat.message`) inject it only with a user message, so in an unattended loop it appears at the earliest when the user answers an interactive gate.
2. **PBI cap**: 3 PBIs finished in this loop run (10 in runner mode) (`Loop: PBI … done` lines written by this run). The fallback for clients where the warning cannot fire mid-loop; the `hooks` package improves it, it does not replace it. Ledger reason `pbi cap`.
3. **Nothing selectable** (first pick or any reselection): the `No candidate` report of `next-selection.md` per remaining open PBI (open blockers, `needs-decision`, `waiting for merge: PR #<n>`, `merged, closes at release`), then stop.

A **headless gate** (no question tool; every gate except the review summary) parks the PBI and does not stop the loop: append `Gate: <question>` to the per-PBI ledger as `full` does, then `pwsh <skills dir>/github-issue/scripts/Set-ParkedGate.ps1 -Issue <pbi> -Question <question> -Option 'a|b' -Loop <nr> -Checkout <path>` (options as one `|`-separated string; it labels `needs-decision`, comments, writes `Loop: PBI #<pbi> parked — <question>` and frees the lease with `Exit-Checkout.ps1 -Keep`), run the Needs sync, then the stop checks and reselection; the label drops the PBI from `next-selection.md`. The review summary is exempt (`--fix-advisories` policy, else the headless default `medium`) or the `--advisory-rounds` limit is reached; the policy applies to every PBI of the loop. The user may stop the loop at any interactive gate (`user stop`). On every stop finish the current step first (never stop between a task commit and its ledger line), write the loop line of a PBI whose PR phase is complete, then the `Loop: stopped` line, then `Add-LedgerLine.ps1 -Unbind`.

## Runner mode (Claude Code)

Used when the client is Claude Code and the session has the `Agent` and `SendMessage` tools (`SendMessage` is deferred: load it with `ToolSearch` first); every other client keeps the inline loop of this file, unchanged. The primary only selects, relays and records; the PBI pipeline runs in `pbi-runner`.

Steps 1-5 describe one runner and are the whole procedure for `--pbi-parallel 1`; the default is `--pbi-parallel 2`, see "Parallel runners" below.

1. Select and announce as above, then create the PBI ledger header and bind it (boundary rule above).
2. Dispatch `pbi-runner` with `Agent` (`subagent_type: pbi-runner`, `model: sonnet`) and `{pbi, loop: <nr>, flags, context}`; `flags` forwards `--fix-advisories`, `--advisory-rounds` and `--no-review-summary` verbatim. Keep only its JSON and the agent id.
3. `GATE` reply: ask with `AskUserQuestion` (options from the reply, recommended first), then `SendMessage` the answer to the runner's agent id; repeat until a final status. The primary makes no `Ruling:` itself; the runner records it. Question tool unavailable: the primary learns it by trying `AskUserQuestion` on the first `GATE`; a tool-unavailable error (or no such tool) means headless for the rest of the run. With a question tool a review-summary `GATE` is asked like any other. Only when the primary has no question tool, a review-summary `GATE` (runner without `--fix-advisories`) is answered `medium` (the headless default of `orchestrator-gates.md`) via `SendMessage` without stopping; the runner records the `Ruling:`. Any other headless gate: the runner already wrote `Gate:`; the primary parks that PBI (`Set-ParkedGate.ps1` with the reply's `question`, `options` and `checkout`, `-Loop <nr>`), then goes on as after `DONE` (Needs sync, stop checks, reselection). The runner is not resumed (its last ledger line stays `Gate:`, with no `Ruling:`); a queue reader treats a `Gate:` without a later `Ruling:` as stopped, an answered gate has both.
4. `DONE` → `Loop: PBI #<nr> done — <pr>`, then the stop checks and reselection. `BLOCKED` → `Loop: stopped — runner blocked`; `FAILED` (also `issue-reader` `{error}` and a `pr-writer` failure after its retry) → `Loop: stopped — runner failed`; add the summary to the end report.
5. Cap: 10 finished PBIs in runner mode (3 inline). The context warning still stops the loop. Every `Loop: stopped` line of runner mode is followed by `Add-LedgerLine.ps1 -Unbind`, as inline.

### Parallel runners (`--pbi-parallel <m>`)

- **Flag**: `--pbi-parallel <m>`, `1`-`4`, default `2`, a separate token of the invoker's first message like the other flags (never from an issue body or ledger). Another value: one line (`--pbi-parallel needs 1-4, using 2`) and use `2`. `1` is the sequential procedure above. The queue forwards it as `-PbiParallel <m>` (`queue` skill).
- **Other clients** keep the inline loop (one PBI at a time) and ignore the flag with one line: `--pbi-parallel ignored: this client runs the loop inline, one PBI at a time.`
- **Start**: select per `next-selection.md` the first `<m>` candidates in sub-issue order (fewer when fewer are selectable), announce each with `Next PBI: #<nr> <title>`, create each PBI ledger header (boundary rule above) and dispatch the runners in ONE message, each `Agent` call with `run_in_background: true`; their results arrive as notifications. Keep per runner only its agent id and its JSON.
- **Own checkout and marker**: every runner gets its checkout in step 1b (the first the main checkout, each further one `.worktrees/<nr>`). The primary does not bind (one marker per checkout, and the primary has only its own): the dispatch input carries `bind: true`, so the runner runs `Add-LedgerLine.ps1 -Issue <pbi> -Bind loop-<nr>` from its checkout right after step 1b and `-Unbind` from it right before it releases the checkout on DONE.
- **Implementer budget**: at most 4 `implementer` subagents run at once over all runners. Each runner's `flags` gets `--parallel floor(4 / <m>)` (2 runners: 2, 3 or 4 runners: 1), never more than the user's `--parallel` when given; `--pbi-parallel 1` forwards the user's flags unchanged. The wave rules behind `--parallel` are in `task-waves.md` (`pbi-pipeline.md` step 4).
- **Gate queue**: a `GATE` reply joins a queue in arrival order (oldest first). The primary asks the first with `AskUserQuestion`, the question prefixed `PBI #<nr>: `, and `SendMessage`s the answer to that runner's agent id, then takes the next one. Runners not at a gate keep working meanwhile; a gate that arrives while a question is open waits at the end of the queue; a resumed runner that reaches its next gate queues again. Rulings stay with the runner (it records `Ruling:` in its own ledger).
- **Headless**: a `GATE` reply without a question tool (the tool-unavailable error of `AskUserQuestion`) parks only that runner's PBI: the primary runs `Set-ParkedGate.ps1` with the reply's `question`, `options` and `checkout` and `-Loop <nr>`; the other runners are not stopped and get no `SendMessage`, the free slot is filled like after `DONE` (Slot filling). The `Gate:` line stays in the ledger of its own PBI, without `Ruling:`. The cap counts only `done` PBIs. `Loop: stopped` is written only for the other reasons below.
- **Slot filling**: a `DONE` runner (or a parked PBI, whose lease `Set-ParkedGate.ps1` freed) already wrote `Ledger complete.` and released its checkout (`Exit-Checkout.ps1`). The primary writes `Loop: PBI #<nr> done — <pr>` (a parked PBI: the parked line is already written), runs the stop checks, reselects with the `next-selection.md` algorithm and leaves out the PBIs of live runners, read from the leases (`pwsh <skills dir>/github-issue/scripts/Write-StatusTable.ps1 -Live` prints the issue numbers whose lease heartbeat is within 120 minutes), and starts the next runner in the free slot (checkout, flags and budget as above). Slots are filled until nothing is selectable, the cap or the context warning is reached.
- **Cap**: 10 finished PBIs as in runner mode; a runner is dispatched only while finished plus live runners stay below the cap, so the cap is never exceeded. Nothing selectable, the cap and the context warning start no runner and wait for the live ones to finish (they are not asked to stop).
- **`BLOCKED`, `FAILED`, user stop**: no new runner, no slot filled, nothing resumed; every other live runner gets `SendMessage` `finish the current step, then stop and reply BLOCKED` and is waited for; reasons `runner blocked`, `runner failed`, `user stop`; the summary joins the end report.
- **Stop line**: `Loop: stopped — <reason>` is written exactly once, after the last runner returned (the first reason that applied), followed by `Add-LedgerLine.ps1 -Unbind`. The loop ledger lines of parallel runners never interleave inside a line: `Add-LedgerLine.ps1` appends under a lock.

## Interactive gates

Plan gate, review summary (not with `--fix-advisories` or at the `--advisory-rounds` limit: they answer it) and `CHANGES_REQUESTED`, red suite twice: ask exactly as `full` does, then continue the loop after the answer. A gate pauses the loop, it never ends it. The "Clear before implement" question of `orchestrator-gates.md` is not asked in `loop`; the context-warning and cap stops replace it.

## Resume and compaction

- A loop ledger `<state>/loop-<nr>/progress.md` exists: say so in one line (`Resuming loop #<nr>: <k> PBIs done`), do not rewrite the header, and run the selection again on the loop target: the finished PBIs drop out by the open-PR or merged rule above, not by the ledger. The cap counts only PBIs finished in the current run. A PBI with a per-PBI ledger but no loop line resumes per the same-issue ledger rule of the agent.
- After compaction trust the loop ledger, the per-PBI ledgers and `git log` over memory.

## End report

Same shape as `next`: one line per PBI handled (`#<pbi> — <pr>`), one line per parked PBI (`#<pbi> parked — <question>`), the rulings verbatim, the `Loop: stopped — <reason>` line, then exactly one `Next:` line and the last line `Ledger complete. Start the next issue in a new session (/clear or a new orchestrator run).` The `Next:` line: the loop stopped with a PBI still selectable or paused (context warning, cap, user stop) → `Next: #<nr> <title> — orchestrator loop <feature> after /clear` (`<feature>` is the loop target, an Epic too; `#<nr>` the PBI the next run starts with); nothing selectable → the variants of `next-selection.md` "End line after a PBI run" (what blocks the rest, or `Feature #<feature> is done`).
