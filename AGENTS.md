# apm-hub — Working in this repository

apm-hub is a marketplace of **skills** (agentskills.io `SKILL.md` format) distributed as APM packages. Skills load unchanged on GitHub Copilot, Claude Code and OpenCode. Workflows are skills. The one `agents` package ships four **agents** that skills cannot replace: the `dev-workflow` orchestrator (primary agent, keeps only phase summaries in context) and the `explorer`, `reviewer` and `implementer` subagents it delegates to, each with its own model and tool set. Entry points beyond skill names: `/orch` (prompt) and `dev-workflow` (agent).

## Layout

```
packages/<domain>/
├── apm.yml                    # name, version, description, skills list (agents list for the agents package)
└── .apm/
    ├── skills/<name>/         # SKILL.md (+ scripts/ references/ templates/ assets/)
    ├── agents/<name>.agent.md # agents package only; one source per agent, see docs/concepts/agent-frontmatter.md
    ├── prompts/               # *.prompt.md (development-workflow only)
    └── issue-templates/       # GitHub issue templates (github package only)
.github/skills/check-prerequisites/   # the only repo-local skill (contributor tooling)
.github/ISSUE_TEMPLATE/               # copy of packages/github/.apm/issue-templates/
src/                                  # TypeScript generators for docs/*.md (Vitest tests)
scripts/check-manifests.mjs           # apm.yml skills list ⇄ directories on disk
apm.yml                               # marketplace: lists all packages
```

`apm_modules/` and `.claude/` are local install state and gitignored. `docs/skill-list.md`, `docs/agent-list.md`, `docs/template-list.md` and `docs/instruction-list.md` are generated by CI on `main`; never commit changes to them in a branch.

## Packages and skills

| Package | Skills |
|:--|:--|
| `shared` | `implementation` (every change has tests; dispatches to `<lang>-implementation`), `detect-techstack` (JSON stack report), `code-review` (severity-rated review using each language's `## Review rules`) |
| `development-workflow` | `orch-pipeline` (plan → TDD → review fan-out → commit, `/orch`), `review-fanout`, `verify-project`, `issue-planning`. Depends on `github`, `shared` and all language packages. |
| `github` | `github-issue` (routing skill for the Epic→Feature→PBI→Task hierarchy; references for standalone, batch, sub-issues, conventional commits, release branches), `github-pull-request` (targets the release branch, not `main`), `github-release` (cut `release/<x.y>`, finish with the release PR into `main`; owns the git-cliff changelog, `references/cliff-setup.md`) |
| `dotnet` | `dotnet-implementation`, `dotnet-test`, `dotnet-create-solution`, `dotnet-mcp-server-generator` |
| `ts` | `ts-implementation`, `ts-test`, `ts-create-project`, `ts-mcp-server-generator`, `ts-pnpm-workflow`, `setup-prettier-eslint-husky` |
| `py` | `py-implementation`, `py-test`, `py-create-project`, `py-uv-cli` |
| `ng` | `ng-implementation`, `ng-test`, `ng-component`, `ng-create-project`, `ng-signal-store`, `ng-ag-grid-developer` |
| `agents` | `dev-workflow` (orchestrator, primary agent: plan → explore → implement per task → review → PR), `explorer` (read-only, haiku, ≤ 300 words), `reviewer` (read-only + tests, findings JSON for `review-fanout`), `implementer` (one task, `implementation` preloaded, ≤ 150-word report) |
| `apm-tooling` | `skill-write`, `skill-audit`, `skill-update`, `skill-slim` (contributor tooling, not part of `all`) |
| `all` | meta-package: every package above except `apm-tooling` |

Every language package provides `<lang>-implementation` (conventions + `## Review rules`) and `<lang>-test`. `detect-techstack` returns their names so `implementation`, `code-review` and `verify-project` can dispatch.

## Skill conventions

- Frontmatter: `name`, `description`, optional `license`, optional `metadata`, plus the optional client keys `disable-model-invocation` (paired with `metadata.opencode/autoinvoke: 'false'`), `user-invocable`, `context: fork`, `agent` — see [docs/concepts/skill-frontmatter.md](docs/concepts/skill-frontmatter.md). Nothing else (no `allowed-tools`, `model`, `compatibility`).
- `SKILL.md` ≤ 100 lines (enforced by `src/generators/skill-size-validator.test.ts`). Long material goes to `references/` (loaded conditionally), templates to `templates/` or `assets/`, repeatable procedures to `scripts/*.ps1`.
- Shell blocks use ` ```powershell `. Scripts are PowerShell 7+ and are invoked as `pwsh scripts/<Name>.ps1`; paths inside a skill are relative to the skill directory.
- Compose, don't duplicate: one skill owns a workflow, others delegate by name.
- Rules live in `packages/apm-tooling/.apm/skills/skill-write/references/skill-writing-rules.md`.

## Agent conventions

- Source format is Copilot style (`name`, `description`, `tools` aliases, `user-invocable`) plus a `metadata:` block with `claude:` and `opencode:` sections; `apmw sanitize` resolves it per platform. Never `model`, `mode`, `permission` or `color` at top level. See [docs/concepts/agent-frontmatter.md](docs/concepts/agent-frontmatter.md).
- Body ≤ 40 lines (enforced by `src/generators/agent-size-validator.test.ts`); it states the return contract and delegates to skills by name.
- An agent is justified only by a model per role, a host-enforced tool set, an output contract or a primary-agent entry point. Everything procedural is a skill.
- After changing an agent, copy it to `apmw/tests/fixtures/agents/` and regenerate the goldens there.

## Commands

```powershell
pnpm install
pnpm run build; pnpm test                 # generators + unit tests (includes the skill size check)
node scripts/check-manifests.mjs --fix    # sync apm.yml skills lists after adding/removing skills
pwsh packages/apm-tooling/.apm/skills/skill-slim/scripts/Get-SkillReport.ps1 -Root .   # sizes, dangling refs, duplicates
```

## Adding or changing a skill

1. Use the `skill-write` skill (or copy `assets/skill-template-optimized.md`) under `packages/<domain>/.apm/skills/<name>/`.
2. Run `node scripts/check-manifests.mjs --fix` and update the package `description` in `packages/<domain>/apm.yml` and the root `apm.yml` if the scope changed.
3. Update the table above.
4. Commit with a conventional message (`feat(ng): …`, `refactor(skills): …`). Consumers pick it up with `apm install`/`apm update`.
