# apm-hub — Working in this repository

apm-hub is a marketplace of **skills** (agentskills.io `SKILL.md` format) distributed as APM packages. Skills load unchanged on GitHub Copilot, Claude Code and OpenCode. Workflows are skills.

## Layout

```
packages/<domain>/
├── apm.yml                    # name, version, description, skills list
└── .apm/
    ├── skills/<name>/         # SKILL.md (+ scripts/ references/ templates/ assets/)
    ├── prompts/               # *.prompt.md (delivery only)
    └── issue-templates/       # GitHub issue templates (github package only)
.github/skills/check-prerequisites/   # the only repo-local skill (contributor tooling)
.github/ISSUE_TEMPLATE/               # copy of packages/github/.apm/issue-templates/
src/                                  # TypeScript generators for docs/*.md, unit tests next to the code (*.test.ts)
test/packages/<domain>/               # Vitest tests of package content (skills, scripts, hooks)
test/repo/ test/helpers/              # repository checks (workflows), shared test helpers
test/integration/skills/              # Copilot SDK harness, own package.json (`pnpm run test:integration`)
scripts/related-tests.mjs             # changed paths → test files (`pnpm run test:related`)
scripts/check-manifests.mjs           # apm.yml skills list ⇄ directories on disk
site/                                 # VitePress docs site: renders docs/ in place, README as home via docs/index.md (see site/README.md)
apm.yml                               # marketplace: lists all packages
```

`apm_modules/` and `.claude/` are local install state and gitignored. `docs/skill-list.md`, `docs/template-list.md` and `docs/instruction-list.md` are generated by CI on `main`; never commit changes to them in a branch.

## Packages and skills

`<state>` below is the orchestrator state directory: `DROMOS_STATE_DIR`, else `<git common dir>/agents` (shared by all worktrees). The working-tree `.agents/` only holds installed skills (`.agents/skills`).

Every language package provides `<lang>-implementation` (conventions + `## Review rules`) and `<lang>-test`. `detect-techstack` returns their names so `implementation`, `code-review` and `verify-project` can dispatch.

## Skill conventions

- Frontmatter: `name`, `description`, optional `license`, optional `metadata`, plus the optional client keys `disable-model-invocation` (paired with `metadata.opencode/autoinvoke: 'false'`), `user-invocable`, `context: fork`, `agent` — see [docs/concepts/skill-frontmatter.md](docs/concepts/skill-frontmatter.md). Nothing else (no `allowed-tools`, `model`, `compatibility`).
- `SKILL.md` ≤ 100 lines (enforced by `src/generators/skill-size-validator.test.ts`). Long material goes to `references/` (loaded conditionally), templates to `templates/` or `assets/`, repeatable procedures to `scripts/*.ps1`.
- Shell blocks use ` ```powershell `. Scripts are PowerShell 7+ and are invoked as `pwsh scripts/<Name>.ps1`; paths inside a skill are relative to the skill directory.
- Compose, don't duplicate: one skill owns a workflow, others delegate by name.
- Rules live in `packages/apm-tooling/.apm/skills/skill-write/references/skill-writing-rules.md`.

## Issues

The title of an issue starts with its level: `[Epic]`, `[Feature]`, `[PBI]`, `[Task]` or `[Bug]`, then the summary (`[PBI] feat: short summary`). The shared `issues.yml` workflow of `GravionLabs/ci` sets the prefix from the level label.

## Tests

- Code in `src/`: unit test next to it as `<name>.test.ts`.
- Package content (skills, scripts, hooks): `test/packages/<domain>/<topic>.test.ts`, `<domain>` is the package of the file under test.
- Repository files outside `packages/` (workflows, `.github/`): `test/repo/`. Helpers shared by several test directories: `test/helpers/` (no `.test.ts` suffix).
- Vitest projects: `unit` (`src/`, `test/repo/`, `test/packages/` files that spawn no process), `scripts` (`test/packages/` files that spawn pwsh, bash or git, listed in `test/helpers/scripts-tests.ts`; add a new spawning test there, `test/repo/vitest-projects.test.ts` enforces it), `integration`, `perf` (`test/packages/**/*.perf.test.ts`, `fileParallelism: false`; a case belongs there when it asserts a wall-clock bound; skipped by `pnpm test`, `test:all`, `test:ci` and `test:related`; own CI matrix job). `pnpm test` = unit + scripts, `test:unit` = unit, `test:all` = unit + scripts + integration, `test:ci` = the same with coverage, `test:perf` = perf.
- A `test/packages` file above ≈ 50 s in `test-results/junit.xml` is split along its `describe`s (shared fixture in `test/helpers/`) before new cases are added.
- Targeted run: `pnpm run test:related -- <paths|--staged|--range a..b>` runs only the tests mapped by `scripts/related-tests.mjs` (the script alone prints the list; `ALL` means run `pnpm test`).
- CI: pull requests run only the tests related to their diff per Vitest project (`scripts/run-related-tests.mjs --project <p> --base origin/<base>`; a project without related tests passes at once); pushes to `main` and `release/**`, `workflow_dispatch` and PRs labelled `ci:full` run every project in full.
- Script tests with many cases: `PwshWorker` (`test/helpers/pwsh-worker.ts`) starts one pwsh per describe (`beforeAll`/`afterAll`) and runs the script in-process per `await worker.run(args, {cwd, env})` (status/stdout/stderr like a spawn); cases that need their own process (PATH without git, stdin, the invoking process's env) stay single spawns with a comment. Fixed-case batches use `runBatch` (`queue-batch.ps1`).
- Resolve repo files from `__dirname` (`path.resolve(__dirname, '../../../packages/...')` in `test/packages/<domain>/`).
- `test/integration/skills/` is the Copilot SDK harness with its own `package.json`; no repo tests there.

## Commands

```powershell
pnpm install
pnpm run build; pnpm test                 # projects unit + scripts (includes the skill size check)
pnpm run test:unit                        # unit project only
pnpm run test:all                         # unit + scripts + integration
pnpm run test:perf                        # wall-clock bound tests, run alone on an idle machine
pnpm run test:related -- <paths|--staged> # only the tests related to the changed paths
node scripts/check-manifests.mjs --fix    # sync apm.yml skills lists after adding/removing skills
pwsh packages/apm-tooling/.apm/skills/skill-slim/scripts/Get-SkillReport.ps1 -Root .   # sizes, dangling refs, duplicates
```

## Adding or changing a skill

1. Use the `skill-write` skill (or copy `assets/skill-template-optimized.md`) under `packages/<domain>/.apm/skills/<name>/`.
2. Run `node scripts/check-manifests.mjs --fix` and update the package `description` in `packages/<domain>/apm.yml` and the root `apm.yml` if the scope changed.
3. Update the table above.
4. Commit with a conventional message (`feat(ng): …`, `refactor(skills): …`). Consumers pick it up with `apm install`/`apm update`.
