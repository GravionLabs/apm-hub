# Contributing to apm-hub

Thanks for contributing. apm-hub is a library of reusable **skills** packaged for APM and usable from GitHub Copilot, Claude Code and OpenCode. [AGENTS.md](AGENTS.md) describes the layout, packages and conventions; this file covers the contribution workflow.

## What belongs here

- Skills that encode a **repo or team convention**, a **tool contract** (schema, CLI flags, non-obvious gotchas), or a **repeatable procedure** (script + templates).
- Fixes to existing skills: contradictions, stale commands, duplicated rules.

What does not belong here:

- Generic best practices the model already knows (tool basics, language tutorials, flag tables).
- Secrets, internal URLs, project-specific identifiers in public packages.
- Agents. Workflows are skills; see AGENTS.md.
- New pipeline features: agents, hooks, queue, ledger, gates, loop. The pipeline is frozen by the [simplification plan](docs/simplification-plan.md); only bug fixes are accepted until Stage A of the [work plan](docs/simplification-workplan.md) removes it.

## Setup

```powershell
pnpm install
pwsh .github/skills/check-prerequisites/scripts/Check-Prerequisites.ps1 -Full
```

The repo uses pnpm (`pnpm-lock.yaml`) only. The Copilot SDK harness that lived in `test/integration` is kept at tag `v2.5.4`.

## Adding or changing a skill

1. Put it under `packages/<domain>/.apm/skills/<name>/` (only repo-contributor tooling goes to `.github/skills/`). Use the `skill-write` skill from `packages/apm-tooling` or start from its `assets/skill-template-optimized.md`.
2. Keep `SKILL.md` ≤ 100 lines; frontmatter only `name`, `description`, optional `license`/`metadata`; shell fences ` ```powershell `. Long specs go to `references/` with a conditional load line, templates to `templates/`, procedures to `scripts/*.ps1`.
3. If another skill already owns a step, delegate by name instead of repeating it.
4. Run the checks:
   ```powershell
   node scripts/check-manifests.mjs --fix
   pnpm run build; pnpm test
   pwsh packages/apm-tooling/.apm/skills/skill-slim/scripts/Get-SkillReport.ps1 -Root .
   ```
   Tests live in two places: unit tests of the TypeScript tools next to their code (`src/**/*.test.ts`), tests of package content (skills, agents, scripts, hooks) in `test/packages/<domain>/` (repository checks in `test/repo/`, shared helpers in `test/helpers/`).
   Vitest has one project (`vitest.config.ts`): `src/**/*.test.ts`, `test/repo/` and `test/packages/`. `pnpm test` runs it, `pnpm run test:ci` adds coverage (CI), a single file runs with `pnpm vitest run <path>`.
5. Update the package `description` in `packages/<domain>/apm.yml` and the root `apm.yml` when the package scope changed, and the skill table in AGENTS.md.
6. Open a PR with a conventional-commit title (`feat(py): …`, `fix(github): …`). The changelog is generated from commit messages with git-cliff.

## Generated files

`docs/skill-list.md`, `docs/template-list.md` and `docs/instruction-list.md` are regenerated by CI after each merge to `main`. The `No Generated Files in PR` check fails if a PR touches them. If you changed a generator in `src/`, test it locally and leave the generated output out of the commit.

## Docs site

`site/` is a VitePress site that renders `docs/` in place; the home page is the hero and feature landing page `docs/index.md`; the root `README.md` is the GitHub landing page only. Preview it with `pnpm --filter site dev`. A local build needs the generated lists first: `pnpm run generate:all`, then `pnpm --filter site build`. A PR touching `site/**`, `docs/**` or `README.md` runs the "Build the site" check (`.github/workflows/pages.yml`). Only `main` deploys, and only while the repository variable `DEPLOY_PAGES` is `true`; the site is at <https://gravionlabs.github.io/apm-hub/>. Do not commit the generated `docs/*-list.md`. Details in `site/README.md`.

## Public surface and renames

Public surface is everything a consumer can depend on: package names (install names in `apm.yml` and the marketplace), skill names, agent names, entry points.

- Announce every rename in the PR body and in the release notes.
- Where an alias or compat path is cheap, add it and announce it as deprecated in the PR body and release notes. It lives at most until the next major, and gets a removal version in the legacy table below at the moment it is added.
- Batch breaking renames into one major release (empty `+semver: major` commit, see Releases). Only that dedicated empty release commit carries `+semver: major`; no other commit does, and none carries `BREAKING`.

## Issues

Use the templates in `.github/ISSUE_TEMPLATE/` (Epic → Feature → PBI → Task, Bug). Children are linked as native GitHub sub-issues; see `packages/github/.apm/skills/github-issue/references/sub-issues.md`.

The title of an issue starts with its level: `[Epic]`, `[Feature]`, `[PBI]`, `[Task]` or `[Bug]`, then the summary (`[PBI] feat: short summary`). The shared `issues.yml` workflow of `GravionLabs/ci` sets the prefix from the level label.

## Releases

Releases are cut from a single rolling branch, `release/next`. GitVersion increments the minor version by default on that branch (`GitVersion.yml`).

- Major: add an empty commit with `+semver: major` in its message when finishing the release. Renames and removals of legacy names ship here, see [Public surface and renames](#public-surface-and-renames).
- Patch: fix on `main` as a hotfix, then merge `main` into `release/next`.
- Parallel lines: use `release/<x.y>` branches.

Details: `packages/github/.apm/skills/github-issue/references/release-branches.md`.
